# STM32H757 双核本地升级闭环实施指导

本文指导在不接入 HTTP 的情况下，先完成并验证 STM32H757 双核固件的本地 A/B 升级闭环。这里的“本地”指通过 ST-Link、STM32CubeProgrammer 或受控测试工具直接把镜像写入空闲槽，再验证启动、健康确认和回滚。

本阶段的目的，是先证明 Flash 写入、镜像校验、EEPROM pending、固定引导程序、CM4 协调和失败回滚彼此能闭合。HTTP 只是后续的数据传输入口，不能替代这一步。

## 1. 目标和原则

目标流程：

```text
生成目标槽镜像
  → 写入当前运行槽之外的空闲槽
  → 读回并校验完整镜像
  → 写入 EEPROM pending
  → 复位
  → 固定 Bootloader/Stub 选择 pending
  → 新应用试启动
  → 健康确认后提交 verified
  → 失败时回到旧 verified 槽
```

必须遵守：

1. 永远不擦除当前运行槽。
2. 永远不擦除固定引导区、CM4 Stub 区和 OpenAMP 共享区。
3. 写入完成且完整校验通过前，不写 pending。
4. pending 持久化成功且读回确认前，不报告升级成功。
5. 新应用未完成健康确认前，不提交 verified。
6. 任何中断电、写入失败、摘要不匹配和启动失败都应保留旧 verified 可启动。

## 2. 当前工程基线和必须核对事项

当前槽位约定：

| 区域 | 地址 | 大小 | 说明 |
| --- | ---: | ---: | --- |
| CM7 固定区 | `0x08000000` | 128 KiB | 应由固定 Bootloader 使用 |
| CM7 A | `0x08020000` | 384 KiB | 槽索引 0 |
| CM7 预留区 | `0x08080000` | 128 KiB | 不作为应用槽 |
| CM7 B | `0x080A0000` | 384 KiB | 槽索引 1 |
| CM4 固定区 | `0x08100000` | 128 KiB | 应由 CM4 Stub 使用 |
| CM4 A | `0x08120000` | 384 KiB | 槽索引 2 |
| CM4 预留区 | `0x08180000` | 128 KiB | 不作为应用槽 |
| CM4 B | `0x081A0000` | 384 KiB | 槽索引 3 |

当前源码已有 `boot_slot.h`、`boot_eeprom` 和 `cm4_boot_handoff` 辅助代码，但需要单独确认：

- 板上 `0x08000000` 是否真的烧录了 CM7 固定 Bootloader。
- 板上 `0x08100000` 是否真的烧录了 CM4 Stub。
- Bootloader/Stub 是否使用当前 EEPROM 结构版本。
- 固定引导程序是否理解 CM4 槽索引 2/3。
- 固定区是否设置写保护。
- `flash_all.ps1` 是否需要扩展为烧录固定引导区；当前脚本主要面向四个应用槽。

如果上述事项没有确认，不能把“应用能从 A/B 槽启动”当成“升级回滚闭环已经存在”。

## 3. 实施拆分

建议新增或修改以下模块：

```text
Common/Src/bsp_flash_ram.c
Common/Inc/bsp_flash_ram.h
CM7/APP/OTA/app_ota.c
CM7/APP/OTA/app_ota.h
CM7/APP/BOOT/boot_eeprom.c/.h
CM7/Core/Src/main.c
CM7/Core/Src/freertos.c
CM4/APP/OTA 或 CM4/Core/Src/freertos.c
Common/Src/cm4_ota_hold.c
```

职责划分：

| 模块 | 责任 |
| --- | --- |
| Flash RAM 模块 | 擦除、编程、校验、错误码、看门狗喂狗 |
| OTA 状态机 | 目标槽选择、进度、镜像摘要、状态转换 |
| EEPROM 模块 | verified、pending、trial、版本、长度、摘要持久化 |
| 固定 Bootloader | 读取元数据、选择槽、试启动计数、失败回滚 |
| CM4 Stub | 读取 CM4 目标槽并跳转 |
| CM4 hold 模块 | 升级 Bank2 前停止 CM4 业务、DMA 和取指 |
| 应用健康确认 | 初始化成功后提交 pending |

## 4. 第一步：确认固定启动链路

### 4.1 读取固定区和 Option Bytes

使用 Windows PowerShell 调用 STM32CubeProgrammer 或现有设备工具读取：

1. `0x08000000` 固定区内容。
2. `0x08100000` 固定区内容。
3. 两个固定区的向量表和 Reset_Handler。
4. Option Bytes、读保护和写保护状态。
5. EEPROM 当前 verified、pending、trial、版本、长度和 CRC。

将读取结果保存为测试记录，至少包含芯片序列号、时间、工具版本和镜像摘要。

### 4.2 固定 Bootloader 最低行为

固定引导程序必须在跳转前完成：

1. 读取 EEPROM 双备份。
2. 校验记录 CRC 和序号。
3. 校验 pending/verified 槽索引范围。
4. 校验候选镜像完整摘要。
5. 校验向量表初始 SP 和 Reset_Handler。
6. 在跳转前持久化试启动计数。
7. 找不到有效 pending 时回退 verified。
8. pending 启动失败或 trial 耗尽时清除 pending 并回退。

若固定 Bootloader 没有这些行为，应先完成并单独测试固定引导程序，再继续应用层 OTA。

## 5. 第二步：设计镜像元数据

每份发布镜像应附带元数据：

```text
目标核：CM7 或 CM4
目标槽：A 或 B
链接地址：槽基地址
镜像长度：实际有效字节数
版本号：单调递增或明确的版本策略
CRC32：完整镜像摘要
可选 SHA-256：完整镜像摘要
硬件型号：STM32H757XIH6 和板型标识
构建批次：用于现场追踪
```

镜像必须使用目标槽对应的链接脚本：

```powershell
make -C Makefile/CM7 APP_SLOT=A
make -C Makefile/CM7 APP_SLOT=B
make -C Makefile/CM4 APP_SLOT=A
make -C Makefile/CM4 APP_SLOT=B
```

CM7 A 镜像的向量表必须位于 `0x08020000`，CM7 B 镜像必须位于 `0x080A0000`；CM4 同理。不要只改变烧录地址而继续使用另一槽的链接镜像。

## 6. 第三步：实现 RAM Flash 操作

### 6.1 必须放入 RAM 的内容

在同 Bank 的空闲槽进行操作时，应确认以下内容不依赖正在擦写的 Flash Bank：

- 擦除和编程函数。
- 函数调用的辅助函数。
- 必需的常量和查表数据。
- 必要中断服务程序。
- 超时和错误处理路径。
- 看门狗喂狗路径。

`.RamFunc` 属性本身不足以证明安全。链接脚本必须把该 section 放到可执行 RAM，启动代码必须完成加载地址到运行地址的复制，并通过 map 文件检查实际地址。

### 6.2 编程规则

STM32H7 Flash 编程使用 32 字节 Flash word。实现时必须：

1. 检查目标地址位于指定空闲槽。
2. 检查长度不超过槽容量。
3. 检查地址按 32 字节对齐。
4. 对最后不足 32 字节的数据按约定填充，并把真实长度存入元数据。
5. 每次编程后检查 HAL 返回值。
6. 失败时停止推进 OTA offset。
7. 写入结束后执行 D-Cache clean/invalidate，避免读回旧缓存。

擦除时只擦目标槽覆盖的 sectors，不触碰预留区、固定区和当前运行槽。

### 6.3 Flash 单元验证

先不接入网络，使用固定测试数据验证：

- 擦除后的区域读回全为擦除值。
- 32 字节对齐地址写入成功。
- 跨多个 sector 写入成功。
- 长度不是 32 的倍数时写入成功。
- 故意写入越界地址会被拒绝。
- 模拟 HAL 错误时不会继续写 pending。
- 读回摘要与输入摘要一致。

## 7. 第四步：实现本地 OTA 状态机

推荐状态：

```text
IDLE
  → PREPARING
  → WRITING
  → VERIFYING
  → PENDING
  → REBOOTING
  → TRIAL
  → CONFIRMED
```

错误路径统一进入：

```text
ERROR → ABORTING → IDLE
```

状态转换要求：

| 状态 | 进入条件 | 允许动作 |
| --- | --- | --- |
| `IDLE` | 无会话 | 创建升级会话 |
| `PREPARING` | 目标核和空闲槽已确认 | hold CM4、擦除目标槽 |
| `WRITING` | 擦除成功 | 写入并推进 offset |
| `VERIFYING` | 已收到完整镜像 | 读回并校验 |
| `PENDING` | 摘要和向量表通过 | 写 EEPROM pending |
| `TRIAL` | 复位并启动候选槽 | 运行健康检查 |
| `CONFIRMED` | 健康检查通过 | verified 切换完成 |
| `ERROR` | 任一步骤失败 | 清理并保留旧 verified |

目标槽选择必须基于实际运行槽：

```text
CM7 运行 A → 写 CM7 B
CM7 运行 B → 写 CM7 A
CM4 运行 A → 写 CM4 B
CM4 运行 B → 写 CM4 A
```

## 8. 第五步：CM4 升级协调

升级 CM7 镜像时，CM4 可以继续运行；升级 CM4 镜像时，CM7 必须先让 CM4 进入安全 hold 状态。

建议在 SRAM4 共享区中定义带 magic、版本和 generation 的 mailbox：

```c
typedef struct {
    uint32_t magic;
    uint32_t generation;
    uint32_t request;
    uint32_t acknowledge;
    uint32_t error;
} cm4_ota_mailbox_t;
```

协议：

```text
CM7 写 REQUEST_HOLD
  → 通过 HSEM/OpenAMP 通知 CM4
  → CM4 停止相机、DMA、外设和业务任务
  → CM4 写 ACK_HELD
  → CM4 停止执行可能访问 Bank2 的代码
  → CM7 验证 ACK_HELD
  → CM7 擦写 CM4 空闲槽
  → CM7 写 RELEASE 或 RESET
  → CM4 恢复或由 Stub 重新启动
```

必须有超时和取消路径：

- CM4 未及时 ACK，CM7 不得擦写。
- 客户端中断或 Flash 出错时清除 hold 请求。
- CM4 收到取消后恢复业务。
- ACK 必须表示目标 Bank 访问已经停止，而不是只表示消息已收到。

当前工程的 OpenAMP resource table 和共享区从 `0x38000000` 开始规划；新增 mailbox 必须避开 resource table、vring 和已有共享数据。

## 9. 第六步：pending、健康确认和回滚

建议状态转换：

```text
verified=A, pending=none
  → B 写入完成
  → B 读回摘要通过
  → pending=B, trial=3 持久化
  → 复位启动 B
  → 初始化完成并通过健康检查
  → verified=B, pending=none
```

健康确认应在以下条件都成功后进行：

- 时钟和 MPU/cache 初始化成功。
- 关键外设初始化成功。
- CM7/CM4 IPC 建立并完成心跳。
- 摄像头和必要业务初始化成功。
- 看门狗已正常工作。
- 应用持续运行了约定时间。

不要在 `main()` 刚进入时立即提交 pending。提交接口必须检查 EEPROM 保存返回值，并在写入后读回确认。

失败路径：

```text
候选槽启动失败
  → 看门狗复位
  → Bootloader 消耗 trial
  → trial 未耗尽，允许再次试启动
  → trial 耗尽，清除 pending
  → 回到旧 verified
```

## 10. 本地测试矩阵

### 10.1 正常流程

1. A 槽运行正常。
2. 生成链接到 B 槽的合法镜像。
3. 擦除 B 槽并写入镜像。
4. 读回完整镜像并比较 CRC32/SHA-256。
5. 设置 B 为 pending，trial=3。
6. 复位并确认从 B 启动。
7. 应用健康确认后确认 verified 已变为 B。

### 10.2 错误流程

逐项测试：

1. 镜像超过槽容量。
2. 镜像链接地址错误。
3. 目标核错误。
4. 向量表 SP 越界。
5. Reset_Handler 越界或非 Thumb 地址。
6. CRC/SHA-256 不匹配。
7. Flash 擦除失败。
8. Flash 编程失败。
9. EEPROM 写入失败。
10. EEPROM 读回不一致。
11. 新应用故意不健康。
12. trial 耗尽后回滚。

### 10.3 断电流程

在以下时间点断电并重新上电：

- 擦除目标槽期间。
- 写入中间 chunk 后。
- 完整镜像写入、pending 写入前。
- pending 写入过程中。
- pending 写入完成、复位前。
- 候选槽第一次启动期间。
- 健康确认前。

每次都应确认旧 verified 槽仍可启动，EEPROM 双备份不会导致无法选择有效槽。

所有固件构建和烧录使用 Windows PowerShell。建议为每次测试记录：


## 12. #questions

1. 当前板上是否已有可读取源码或二进制的 CM7 Bootloader 和 CM4 Stub？
2. Bootloader 是否已经实现 trial 递减、健康确认和回滚？如果没有，固定引导程序是否纳入本项目范围？
3. EEPROM 的真实器件容量、写周期和掉电保护方式是什么？
4. CM4 在当前系统中是否会执行来自 Bank2 的代码、使用 Bank2 常量或启动时 DMA 访问 Bank2？这决定 hold 协议的安全边界。
5. 健康确认的最小标准是什么：只检查双核 IPC，还是必须包含摄像头、LCD、网络和业务心跳？
6. 是否允许首版只支持单核升级，待 CM7/CM4 单独闭环后再支持成套升级？本文建议先单核。

## 13. 完成标准

本地升级闭环只有在以下项目全部通过后，才可作为 HTTP OTA 的底层：

- 四种核/槽镜像均能按正确链接地址生成。
- 空闲槽擦除、32 字节编程和读回校验稳定。
- 目标槽、长度、向量表和完整摘要检查有效。
- EEPROM pending 写入和读回检查有效。
- 新应用健康确认后 verified 才切换。
- 新应用启动失败能回滚。
- 断电测试不会丢失旧 verified。
- CM4 hold/ack/cancel 在升级 Bank2 时可靠。
- 固定区和共享区不会被 OTA 擦除。
