# 保持画质的 MJPEG 帧率优化

用户确认保持 800×480、JPEG 质量 80 与现有 4:2:0 色度采样，采用实测后针对性优化，并进行 Windows 构建与实机验证。

## 基线与范围

设备 192.168.10.2 当前运行 CM7 B 槽，两观看端连接时 `/status` 报告 7.7 FPS。COM7（115200、8-N-1）日志显示快照复制 42～44 ms、编码 86～87 ms，每帧生产约 129 ms。Qt 实时预览工程为 `../qt-camare`，接收线程内完成 JPEG 解码与人脸检测，界面每 33 ms 获取最新图像。

## 实施设计

- 保持现有快照、整帧转换、硬件 JPEG 和三输出缓冲架构，以及双观看端独立发送机制。
- 快照仍按 16 行分块复制、逐块失效缓存，复制期间保持帧保护；将每块固定等待改为累计工作 4 ms 后等待一 tick，减少固定空闲时间。
- 仅对 `jpeg_utils.o` 使用 `-O2`，其余代码保留现有调试优化级别；颜色转换算法和图像参数不变。
- 首轮不调整 TCP 参数，用实测判断发送是否成为下一瓶颈。
- 编码分段计时确认颜色转换约 40～42 ms、JPEG/MDMA 约 37 ms 后，将 MDMA 的 SDRAM 端改为 32 位递增、8 beat 突发，FIFO 端维持固定地址单次传输及 32 字节请求。同步修改 CubeMX 配置源与生成代码；所有现有输入输出缓冲均满足字对齐，传输长度保持不变。
- 每 30 帧输出颜色转换与 JPEG/MDMA 耗时，辅助后续定位瓶颈。
- 保留相机错误恢复、缓存维护、OTA 停流等待与失败恢复。相机出现溢出或花屏时，回退对应实验改动。

## 验证与成功标准

通过 Windows PowerShell 构建 CM7 A/B，检查镜像大小。经现有本地升级脚本向空闲槽更新，确认新应用运行及 confirmed 状态。对比双端观看的 copy/encode 耗时和发送 FPS；运行现有只读 HTTP 测试验证双观看、第三连接 503、完整 800×480 JPEG、状态响应、断开与重连。使用 Qt 实机测试及现场浏览器、Qt 和 LCD 画面确认验证显示正常。

不预先承诺目标 FPS；以相同场景下实测提高且无采集错误、画面损坏和功能回归为验收依据。构建或模拟通过不能替代实机验收。

## 本轮实测结果

- Windows PowerShell 执行 `make -s -C Makefile/CM7 all-slots -j8` 通过，A/B 的 text 均为 164012 字节，BIN 为 164020 字节，小于每槽 393216 字节。链接器仍提示 RWX LOAD segment 警告。
- 通过现有本地升级脚本更新并校验 CM7 A 槽；随后状态为 `running=0`、`active=0`、`flags=0x00`、`trial=0`，说明已运行并完成应用确认。板上 B 槽保留上一轮仅含分段计时的版本；磁盘 A/B 构建产物均包含最终优化。
- JPEG/MDMA 阶段由约 37 ms 降至 7～8 ms；颜色转换约 38～44 ms。双端观看时快照耗时随发送负载变化，观察到约 20～36 ms。
- 浏览器和 Qt 同时观看时，连续五次 `/status` 分别为 12.0、11.9、12.0、12.1、12.0 FPS。相对基线 7.7 FPS 提升约 56%。用户确认两端约 12 FPS、画面正常。
- `tests/http/mjpeg_test.ps1 -Device 192.168.10.2 -Frames 20` 通过：双连接多帧完整解码、800×480 尺寸、第三连接 503、状态响应、单端断开后另一端继续及重连。双端观看期间额外读取串口 20 秒，未观察到相机或编码错误；这不代表长时间压力测试已完成。
- 中途本地升级预检查曾因 EEPROM 不可用而拒绝，启动日志显示 `BSP EEPROM not ready, status=1`。用户彻底断电重启后恢复，后续升级成功；本轮未修改 EEPROM 或 Bootloader 实现，该故障原因未进一步定位。
- Qt 工程源码无需修改；现场使用已有程序确认了本轮预览效果。未另行运行 Qt `--device-test`，以免占用正在进行双端观看的连接。
